# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- The webhook recognises more than a labelled issue. A new comment on an issue or a pull request, a submitted review, a completed check suite or check run, and an issue that is closed, reopened or loses the `factory` label are stored in `ingress` with the outcome `routed` and a code that names what happened. Nothing acts on them yet: a routed delivery creates no task and queues no job. Tasks have a `cancelled` stage that no run enters yet, shown under "Needs a person". The Setup page has a "Webhook events" line that reads what the GitHub App subscribes to and names the events it does not receive, with a link to the App settings (#59)
- Before it changes anything in a new task, the builder writes a plan: the files it will change and why, the order, the risks, the tests that prove it and what it leaves out. The plan is stored, shown in the pull request and on the task page, and given to the reviewer, together with the changed files the plan does not name; the build continues the session that wrote it, and a task sent back keeps its plan instead of planning again (#33)
- The review no longer approves a change that weakens a test that was there before it: a test case removed, fewer assertions, or a skip, `only` or todo added. It is a blocker in an issue labelled `bug` and major otherwise; when the issue names the file or the test, the reviewer decides (#34)
- The `watch-promotions` cron watches the open promotion pull requests of every enabled repository (`workspace` into `develop`, `develop` into the release branch, and the Version Packages pull request). A GitHub Actions job that failed is rerun once; when it fails again, or when a check such as CodeQL fails, the factory opens an issue with the `factory` label carrying the check, the run and the error lines of its log, so an agent fixes it without anyone reading the log first. The same failure on a later commit is a comment on its issue. A secret scanner's failure gets an issue without the label, for a person. `FACTORY_PROMOTION_ISSUES_PER_PASS` caps the new issues per repository and pass (three by default) (#31)
- The factory measures itself every hour: first-pass checks, rework rounds, first-review approval, time to first review and to delivery, cost per delivered run, change failure and hours to release, per repository and for all of them, as daily points. Each series is read against a control band (mean and standard deviation of the 30 days before its last 8 points, with the Western Electric rules, in the direction that is worse). A drift is only recorded, a run out of band shows on the Health page, and a point beyond 3 sigma opens an issue, once per metric and repository within the window. Detection uses no model (#32)
- Sandboxes can run on E2B with `FACTORY_SANDBOX=e2b` and `E2B_API_KEY`, under the same domain allowlist, with credentials attached outside the sandbox and renewed while a run works; a run plans its agent passes for the hour E2B's free plan allows, or for `E2B_MAX_SESSION_MS` (#26)

- An evaluation suite of 30 tasks the factory delivered, in six repositories, run by the real agents along the factory's path (sandbox, checks, diff guards, review, rework) without pushing anything. `pnpm evals` runs the quick five and compares them with `evals/baseline.json`; `pnpm evals:cases` rebuilds the cases from the database. A deploy that changes a prompt, a harness, a model or the sandbox image now runs the quick cases first and stops, before the build, when the pass rate drops by more than 20 points or the mean cost per case rises by more than 25% (#35)

### Changed

- A task blocked by an issue in its own repository starts once the factory has integrated that issue's fix, instead of waiting for the issue to close at the release; a blocker in another repository still waits for its release (#36)

- A rework that no longer fits in what is left of an E2B session, but fits in the run's 90 minutes, no longer fails with "no time left for another agent pass": the run saves the disk to a snapshot, restores it into a new session under the same network rules, deletes the snapshot and goes on. The task's history shows the new session. A provider that cannot save a sandbox refuses the pass as before (#29)
- When a repository's integration branch requires status checks, the factory no longer merges its pull request after only its own checks: it turns on auto-merge pinned to the verified commit, and once GitHub merges it the factory advances `develop` and makes the pre-release. A required check that fails sends the work back to the agent with what the check reported, up to three times; a push after verification, a closed pull request or auto-merge turned off by somebody go to a person. The panel shows such a task as "waiting for CI" (#25)
- A run may last 90 minutes instead of 50, so a run in a repository with slow checks has room for a rework and the checks again; the GitHub token is renewed every 15 minutes while a run works, in the sandbox's firewall and in the factory's own calls, instead of being taken once and kept until it expired (#4)
- An agent pass may take 45 minutes instead of 25, cut so one more round of checks and review still fits in the sandbox; a rework with less than five minutes left fails with a message saying so, instead of being stopped with the sandbox (#23)
- A check may take 15 minutes instead of 10, so a test suite that takes ten minutes on a busy machine is no longer cut while it passes (#24)

### Fixed

- Work approved after a handoff no longer fails at the last step because its pull request is still a draft. A handoff leaves a draft titled `[needs a person] ...`, and when a person asked for changes and the new run was approved, the factory tried to integrate that same draft. GitHub refused auto-merge on it, and the factory reported a settings problem. Before integrating, it now marks a draft ready for review and gives it back its title without the prefix, whether GitHub merges it through auto-merge or the factory merges it itself. A pull request that is not a draft gets no extra call. If GitHub still answers that the pull request is a draft, the factory marks it ready and asks once more (#56)
- Asking for changes on a task whose branch is not on GitHub (a task resolved with no change, or one whose branch a retry deleted) no longer fails the task at `git fetch` before any agent reads the note. The run starts from the integration branch, as a first run does, with the note in the builder's prompt, and writes a new plan. A task sent back no longer counts as resolved (#54)
- The reviewer no longer asks to remove a file one of the factory's own checks required. When a check failed on an earlier attempt of a task and passes on the commit under review, the review prompt names the check, the line of its output that says why it failed, and the files added between the two commits, and says that a file the check called for is legitimate. Those files are no longer recorded as changed outside the plan. Before, an empty changeset added to satisfy the `changeset` check in a private package was read as outside the plan, the builder could not remove it without failing the check again, and the task failed with "the agent made no change to the repository" (#53)
- A changesets publication no longer ends as soon as the first package release appears. The release workflow creates the releases one package at a time, so the factory used to close issues naming only the versions out at that moment, and could leave out the one that carries the fix. It now reads which published packages the Version Packages merge versioned and waits until each has its release, then ships the tasks with every tag. When a release is still missing 30 minutes after that merge, it publishes with the ones that exist and the publication's detail names the missing package (#52)
- A task no longer fails at the last step when the integration branch requires status checks and they passed before the factory reached it. GitHub refuses auto-merge on a pull request that is already clean, and the factory read that as a settings problem. It now merges the pull request at once, pinned to the verified commit, and advances `develop` as it does where no check is required. A release into a branch that requires checks does the same. Any other refusal fails as before (#51)
- A task that finished with no change now moves from Already resolved to Released once the commit it was resolved at is on the release branch (the one the owner set, or the default branch). Every release that completes, the factory's own or a changesets publication, checks the resolved tasks of its repository against the promoted commit. The `catch-up` cron checks the ones already there, 25 per pass, and a task moved once is never checked again. The `released` stage names the release branch and the resolving commit; no tag is recorded and its issue, closed when it was resolved, gets no comment. A task whose commit is not on the release branch yet stays in Already resolved (#50)
- A changesets publication no longer fails when the release workflow pushed `changeset-release/<release branch>` but did not open the Version Packages pull request, as happens where the organisation does not let Actions open pull requests. When that branch is ahead of the release branch, was committed after the promotion and has no pull request, the factory opens Version Packages from it, naming the promoted commit, and the publication keeps waiting until it merges that pull request as usual. A branch committed before the promotion is ignored, and with no such branch the publication ends as before (#49)
- A task that finished with no change, because the code already did what its issue asks or a person resolved it another way, no longer sits in the Delivered column forever. Delivered now holds only work that waits for a release, and such a task moves to a new Already resolved column, since no release will ever carry it. A task whose work was merged into the integration branch stays in Delivered until a release carries it. The tasks already in that state move on the next load of the panel (#47)
- A release in a changesets repository no longer counts as waiting the changesets that an earlier release already consumed on the release branch while `develop` still holds them. A changeset waits only when the comparison of `develop` with the release branch lists it as added since their merge base; with none added, the release is the factory's own or is refused naming the published package, as for a repository with no changeset. A publication whose release run on the promoted commit finished without opening a Version Packages pull request no longer waits forever: after a 10 minute grace window, when every check on that commit completed, the factory releases the promotion as its own patch version, releases its tasks and closes their issues. When a check failed, or the promotion changed a package changesets publishes, the publication fails and the task page shows why (#48)
- A release in a changesets repository with no changeset waiting is no longer refused when every change since the release branch is in packages changesets never publishes. The factory reads which files `develop` changes, maps each one to the packages it is under, and when none of them is published (private, listed in `ignore` of `.changeset/config.json`, or no package at all) it promotes `develop` and makes its own release: the tag, the released tasks and their closed issues. When a published package changed, the refusal stays and now names the package. The factory's own version now follows the highest `vX.Y.Z` tag of the repository, since in such a repository the latest release is a package's tag (#46)
- A release the factory tags itself now releases every task whose work the promotion carries, not only the one it was asked for. Each finished task whose merge is in the promoted commit moves to released with the tag, and its issue gets a comment naming the version and its release, then is closed; the task that asked for the release is treated the same way. Before, the other tasks stayed done and no issue was closed. An issue GitHub will not close no longer stops the release or a changesets publication: the reason is recorded on that task and in the result (#45)
- When a promotion check fails again on a new commit after the fix for its open issue was integrated, the `watch-promotions` cron now opens a new issue for the factory, linked to the previous one, instead of commenting on an issue nobody works on until the release. While the fix is not integrated yet, the same failure is still a comment on its issue, and the cap on new issues per pass still applies (#44)
- A required check that ran twice on the head commit, as a workflow on both `push` and `pull_request` does, no longer reads as passed when one of its runs failed. GitHub blocks the merge on that failed run, so a release waiting for its checks waited forever instead of being refused. The factory now counts a required check as failed when any run of it on the commit failed: the release is refused with the check's name, and an integration is sent back with the failed run's report. A check whose runs all passed is not failed, and one with no report is still silent (#43)
- An E2B run no longer fails with `2: [unknown] terminated` when the connection to a sandbox that is still alive drops in the middle of a command. The factory reattaches to the command by its pid, up to six times with a pause that grows from 1 to 15 seconds, all within the command's own timeout, and returns its real exit code and its whole output, kept in files inside the sandbox, so the agent's JSON reaches the factory complete. Lines that came while the connection was down reach the task page when the command ends. A sandbox that stopped or does not answer still fails the run at once, and when every reattach fails the error names the command's pid and the last failure (#41)
- The review no longer reads a test case retitled in its own file as a removed one, so a change that has to update a count or a version in a test title can pass. Each new name a test file gains, and that no file in the diff lost, stands for one name the file lost. When the file keeps its assertions, the retitle is only a minor finding that asks the reviewer to check the new title. A case removed with no new one in its file, and a file left with fewer assertions, still stop the approval as before (#42)
- When a required check fails on a pull request in auto-merge, the work no longer goes back to the agent with only a link it cannot open from its sandbox. The `integrate-after-ci` cron reads each failed check on the server with the repository's token and puts its evidence in the note: the error lines of an Actions job's log, or the annotations and summary of any other check, read the same way `watch-promotions` reads them. The link stays in the note. When the required check is an aggregate job whose log only says that a job it depends on did not succeed, the note also names the other checks that failed on the same commit, marked as not required, with their links and error lines. When GitHub will not give the evidence, the note keeps the link and says the log could not be read, the reason goes to the cron's log, and the work is still sent back (#40)
- A release into a branch that requires status checks no longer fails because GitHub refuses to merge a release pull request whose checks have not reported. The factory turns on auto-merge pinned to the head it saw, and the `integrate-after-ci` cron finishes the release once GitHub merges it: the tag, or the publication of a changesets repository, recorded only when the promotion is on the release branch. A required check that fails, a new push to `develop`, a conflict or a check that never reports refuses the release without retrying it, and the task page shows why; only one release per repository waits at a time (#28)
- A promotion job whose rerun GitHub refuses (403 or 404, as when the GitHub App may not write Actions) no longer stops the `watch-promotions` pass for its repository every five minutes without filing anything. The first attempt becomes the evidence: the issue opens in the same pass with the lines of the job's log and says the job could not be rerun, and the refusal stays in the pass's errors so the missing permission shows in the log. Any other failure of the rerun still fails the pass (#39)
- A task sent back is no longer charged with what its integration branch changed after its branch was cut. The review guards now read the change from the merge base, as the reviewer and the pull request do, so a release merged in the meantime no longer shows up as files changed outside the plan, as a weakened or deleted test, as a changed `test` script or as a change to `.github/`. A first run reports the same findings as before (#38)
- After a changesets release, the `publish-changesets` cron also merges the back-merge pull request the repository opens from its release branch into its integration branch, with a merge commit pinned to its head, once its checks are green; while they fail or run it stays open and is tried again a minute later. Until now nothing merged it, so every factory pull request into the integration branch failed its checks and approved tasks were sent back. No other pull request is merged this way, a fork's branch of the same name included (#37)
- A release in a repository that publishes with changesets no longer tags a version of its own that names nothing on npm: it refuses when `develop` holds no changeset, promotes `develop`, and leaves the version to the repository's release workflow; the factory then merges the Version Packages pull request once its checks are green, and when the packages are published it releases every task whose work shipped and closes its issue with the versions. Work on such a repository is also checked with `changeset status`, so a package changed without a changeset is sent back (#27)
- A task whose issue says it is blocked by issues still open no longer runs and lands in Needs a person: it waits in Will retry itself, before any sandbox, and checks again every half hour until each of them is closed (#21)
- A deploy now starts every enabled worker, a stopped one included, so the factory runs as many tasks at once as it has workers; before, a worker that stopped once stayed stopped through every later deploy (#20)

## [0.2.0] - 2026-11-10

### Added

- A failed or handed-over task that a person resolved another way can be marked resolved from its page, with a note saying where; it moves to Delivered (#10)

### Changed

- A done task whose pull request GitHub refused for a conflict with its base now runs again on its own from the new base, up to three times, instead of waiting for a person to press Retry; a merge refused for any other reason still waits for a person (#16)
- A done task whose pull request was never merged, as when GitHub refuses it for a conflict with the base, can be started again from the panel (#14)

### Fixed

- A merge GitHub refuses for a moment no longer leaves a task done with its pull request open: a 5xx or a 405 that says the base branch was modified is asked again, up to four times (#14)
- A run starting while another run makes its docker sandbox no longer removes that run's new network and fails it at the sandbox stage: a network counts as an orphan only once it is as old as a stale container (#15)
- The factory's squash merges no longer gain a `Co-authored-by` trailer for its own bot: each squash commit is named after its pull request, with no body, instead of the message GitHub composes, which lists every commit author; commits are also signed with the bot user's own email, which needs the new `GITHUB_APP_BOT_USER_ID` (#13)
- A repository's test that starts a server on localhost and fetches it no longer fails in the docker sandbox: localhost is named on 127.0.0.1 alone, as on a hosted runner (#12)
- A repository's test that a subprocess is gone no longer fails in the docker sandbox: the sandbox now runs an init that reaps exited orphans (#11)
- A Claude Code run that printed its result before a background command kept it alive past the timeout no longer fails the task (#8)
- The factory can push a change to `.github/workflows`: its installation token now asks for the `workflows` permission (#9)

## [0.1.0] - 2026-11-08

### Added

- An issue labelled `factory` in an enabled repository becomes exactly one task, and a repeated webhook delivery does not create a second (#6)
- Each task runs a coding agent (Claude Code or Codex) in an isolated sandbox with an explicit domain allowlist, with credentials attached outside the sandbox (#6)
- A pull request opens only after the configured checks pass on the pushed commit, and an independent reviewer approves it (#6)
- Failed checks or a review that asks for changes send the work back to the same agent session, and a person takes over after three attempts (#6)
- An agent that needs a decision asks on the issue, and the answer resumes the same session (#6)
- The factory merges its own pull request into `workspace`, tags a pre-release on `develop`, and leaves the release to `main` to a person or, when enabled, an agent's verdict (#6)
- A red `main` after a release opens a revert pull request, which the factory never merges (#6)
- The panel shows the board, the inbox, each task's timeline, evidence, reviews and cost, live, and lets the owner approve, ask for changes and retry (#6)
- The panel lists the repositories the GitHub App reaches, enables them, and sets checks, domains, branches, agents and release mode for each (#6)
- New jobs and plans of several issues can be started from the panel, and the task still comes from the issue's webhook (#6)
- A chat assistant and a guide on each page read the factory's state and ask before changing anything (#6)
- Every agent reads the owner's knowledge base, written as an Open Knowledge Format 0.2 bundle, and notes what it learned (#6)
- The panel shows what the agents do while they work, step by step, and keeps it for 30 days, with known token formats redacted (#6)
- A project can declare its install command, checks and domains in `.factory/setup.json` on its default branch, and its domains open only after the owner approves them (#6)
- The agent is told the exact commands the factory runs on its commit, in the first pass and in every rework (#6)
- An issue the code already resolves is closed with the evidence instead of failing (#6)
- The factory runs as `systemd --user` services, catches up on missed webhooks, and keeps a restorable database backup (#6)

### Fixed

- Claude Code runs on the Docker sandbox no longer fail with `claude: not found` (#1)
- A run started again after its process died can push its branch again (#2)
- A clone that stalls is cut after three minutes and tried again, instead of failing the task after ten (#6)
- A run may last 50 minutes instead of 30, and one that runs out says so instead of failing with `No such container` (#6)
- A check that fails runs once more at the same commit, so a flaky test no longer costs the agent an attempt; both runs stay in the evidence (#6)
- The checks run on a clean tree of the pushed commit, so what the agent left in ignored files no longer decides the result (#6)
- The backup check reads the whole dump and no longer fails with EPIPE on dumps over about a megabyte (#3)
