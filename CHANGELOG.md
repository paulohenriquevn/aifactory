# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- A card on the board shows when its task came back from Delivered and has not been delivered again. A small warning line says why and how long ago: the approved pull request conflicts with a base that moved, a required check failed, the base passes its checks again and the run only merges it, a person asked for changes, or something else. Its tooltip holds the note the run was given. `GET /api/panel/tasks` returns the mark as `returned` (`reason`, `at`, `note`) (#377)
- `FACTORY_PROMOTION_HOLD_MS` sets how long a waiting promotion holds new integrations out of the integration branch (45 minutes when unset). Zero turns the hold off, also for a promotion pinned before: approved work integrates at once, and the promotion's checks start again on each new head (#376)
- The coordinator acts on a handoff whose rework after the review broke the checks (`checks_broke_after_review`), where the branch went back to the reviewed commit. It sends the task back on its branch with what the checks printed on the commit that broke them, or what the GitHub Actions jobs of the pull request's head logged, and escalates it when neither kept anything. It counts as a rework of the checks and is never scoped (#360)
- A publication that has waited three hours is a `publication_stalled` exception, escalated once per publication on the task whose release started it. The release train still holds the repository while it waits, but the hold now shows up for a person. When a check failed on its Version Packages pull request, the escalation names the check and says that only a new promotion ends it (#361)
- `FACTORY_LINE_STOP_SCOPE=fix_first` keeps a red promotion from holding the rest of its repository. The line incident and its one fix issue still open, the fix still goes ahead of the queue by its priority label, and the line still ends only when the promotion is green, but other runs, integrations and coordinator actions go on meanwhile. `hold`, the default, keeps today's behaviour (#370)
- The coordinator acts on the handoffs `integrate-after-ci` writes after the automatic runs. A pull request that still conflicts with its base, or one that still has to merge a base that passes its checks again, gets the base merged into its branch with no agent; required checks that still fail are sent back on the branch with what they reported, or what their GitHub Actions jobs logged. These handoffs now record a `cause` (`pull_conflict`, `base_fixed`, `ci_red`). A required check that never reported still goes to a person (#337)
- When the sandbox provider refuses a sandbox for credit or spending (E2B's `team is blocked: credit_exhausted` or `spend_limit`, Vercel's `Status code 402`), the factory stops starting sandboxes for 10 minutes. A run taken meanwhile goes back to the queue unchanged, for after the pause, and its task stays queued instead of failing and spending its automatic retries. After the pause one run probes the provider: a sandbox that starts ends the pause for every process, and a new refusal starts it over. The log says `sandbox_provider_paused`, `run_deferred`, `sandbox_provider_probe` and `sandbox_provider_resumed` (#340)
- The supervisor reports a repository whose queued runs waited more than an hour while none of its runs started, as a `queue` finding on the Health page. The finding names the cause when it is known: a stopped line, the coordinator's hold for the fix of a failing test, a paused sandbox provider, no run started anywhere, or runners busy with other repositories. It resolves on its own once a run of the repository starts (#342)
- A red promotion of the integration branch now stops the line of its repository, when `FACTORY_LINE_STOP_MODE` is `auto`. The promotion watch files one issue (`factory`, `priority:1`) for every failure of the head instead of one per check, records a `line_incident`, and closes the per-check issues whose fix never integrated as superseded by it. While the line is stopped, the other queued runs of the repository are held, nothing but the fix integrates, and the coordinator acts on nothing else there. The incident ends only once every check of the promotion head passed: a fix that integrated while the promotion stays red gets a second issue, and after two the issue goes to a person with the line still stopped. The board shows each stopped line, for how long, and its fix. `GET /api/panel/tasks` returns them as `stoppedLines`. `trial`, the default, logs what it would do and files as before (#329)
- The board shows, above the metrics, each red integration branch that holds delivered work, how long it has been red and how many tasks it holds (#282)
- The top of the board shows the factory's speed, efficiency and quality. Closed it is one line; open it lists the tasks delivered in the last hour and in 24 hours, the hourly mean, the median lead time of the last day, the tasks queued and working, and the latest day of the first-try checks, cost per delivery, rework rounds, first-review approval, deliveries that came back and handoffs, each marked when it left its band. `GET /api/panel/pulse` serves the live numbers (#272)

- Each card on the board shows the task's lead time, from entering the factory to its delivery, with its status: on track, at risk or overdue. While the clock runs, an at-risk card gets an amber border and an overdue one a red border; a delivered card keeps the time it was delivered in. Each repository sets both limits in minutes on its settings form, 120 and 480 by default (#269)

- The Queued column lists its tasks in the order the worker serves them, the order the scheduler set, with tasks that have no place in the line (held, or not looked at yet) after them. The first ten carry their rank on the card, and a line marks where the rest of the queue starts. The priority of a queued task (`priority:N`) is a badge, P1 red, P2 amber, P3 violet and plain from P4 (#226)
- A coordinator looks at the factory's exceptions every ten minutes (the `coordinate` cron) and decides one action for each from a closed set. Required checks that failed on a run that changed nothing send the task back on its branch with what the checks reported; a review with no usable verdict sends the branch through the checks and the review again; a run the supervisor found stalled or orphaned is retried from its finding as an automatic retry, with no decision in anybody's name. An environment failure past its automatic retries, a fact it could not read and anything else stay with a person. Each decision is recorded once per exception and head in `coordinator_action` (a `trial` decision does not stop `auto` from applying one on the same head) with its reason and outcome (`applied`, `trial`, `refused`, `failed` or `escalated`), and a task gets at most two applied actions before the next one is escalated with the two it tried. `FACTORY_COORDINATOR_MODE` is `off`, `trial` (decide and record, apply nothing) or `auto`, and starts in `trial`. A handoff now records its `cause` (`review_plateau`, `review_unusable` or `checks_unchanged`) next to its reason. The coordinator merges nothing and uses no model (#124)
- Two more indicators in the hourly measure. `handoff_share` is the share of the runs that ended in a day that ended handed to a person. `person_decisions_per_delivery` is the decisions a person recorded that day (approve, request changes, retry, resolve, and a release a person started) divided by the runs delivered that day, the same deliveries that `minutes_to_delivery` and `cost_per_delivery` count; a day with no delivery has no point. What the factory records on its own, a release an agent started or would have started, is not counted. Both get worse going up. With `FACTORY_BASELINE_FROM` set to a date, every pass also compares the mean of each series over the last seven days with the 28 days before that date and logs `better`, `worse` or `no_change`, where `no_change` means the week stayed inside the control band (the baseline mean plus or minus 3 standard errors of the week's mean). A value that is not a date stops the measure with an error (#126)
- The coordinator scopes a review that did not converge (a `review_plateau` handoff) instead of escalating it. A drafter built with `buildAssistant` reads the issue, the task's plan, the findings of every review round and how the blocking findings moved, and answers which requests belong to the issue, which do not, a follow-up issue or none, and a note for the builder. In `auto` the factory files the follow-up on the same repository (labelled `factory` when the repository is enabled, with a last line linking the original issue), appends a `## Scope decision` section to the issue body and sends the task back on its branch with the note. An answer that does not parse is escalated with the parse error, and a draft whose note or in-scope requests name quality configuration (`quality/`, Stryker, `.jscpd`, the CRAP baseline, coverage thresholds) is refused and sends nothing back. In `trial` the model drafts and the draft is recorded, but nothing is written to GitHub. Each draft and its cost are stored on the `coordinator_action` row. The drafter has its own model, `FACTORY_COORDINATOR_MODEL`, by default `openrouter/openai/gpt-4.1-mini` (#125)
- The coordinator files a failure that repeats as an issue for the factory. A failure's signature is the first line of the reason of a `failed` or `handoff` event with URLs, paths, commit ids and numbers replaced by placeholders. A signature seen on three or more tasks in seven days, in at least two incidents an hour or more apart (an outage that stops a whole queue at once is one incident), becomes an issue on `paulohenriquevn/aifactory` with the `factory` label, carrying the signature, each task with its event, reason and time, when it was first and last seen, and a repro. A designed wait (a reason that starts with `blocked by` or `waiting for an answer`) is never filed, a signature is filed once (`failure_signature`), and a pass files at most one issue and the week at most three. Seven days after the issue closes, the coordinator counts the signature in the seven days after the close and in the seven days before the issue was filed, records both, and comments on the issue with both counts when the signature still shows up. An issue whose state cannot be read is not measured on that pass. In `trial` it files and writes nothing and logs what it would file (#127)
- The coordinator releases integrated work on its own in a repository whose release mode is `auto` (its own, or `FACTORY_RELEASE_MODE` when it has none). On each pass it looks at every enabled repository, and when tasks are done and integrated, no task is queued, running or waiting for CI, no release or publication is in flight, and `watch-main` does not report the release branch red or still watched, it calls the same `release()` the panel uses, once per head of `develop`, as `agent:coordinator`. Every refusal of `release()` still applies, and the release does not count as a person's decision in `person_decisions_per_delivery`. A changesets repository follows its changesets; any other release is `major` only when an issue carries the `breaking` label, `minor` when one is labelled `enhancement` or `feature`, and `patch` otherwise. A refusal whose cause can end by itself (required checks still expected, running or never reported, or a head that moved before the merge) is tried once more on the same head, and a second refusal on that head stays refused. A red release branch is recorded as `escalated` and nothing is called. A repository in `trial` gets the decision recorded as `trial`, and one in `manual` is left alone. Each decision is a `coordinator_action` row on the repository's oldest integrated task (#128)
- Integrated work now reaches `develop` without a person when `develop` takes changes only through a pull request. The factory opens its promotion pull request from the integration branch, as before, and turns on auto-merge pinned to the head it saw, so GitHub merges it once `develop`'s required checks pass; a promotion that is already clean is merged at once, pinned to the same head. Only the factory's pull request from the integration branch of the same repository into `develop` gets it, never one from a fork or another branch. While the promotion waits, new integrations are held out of the integration branch for 45 minutes at most (`promotion_wait.hold_until`), so its checks are not restarted by every merge. A held task waits in `done` and is integrated on the first `integrate-after-ci` pass after the hold expires or the promotion merges. When the head moves before auto-merge is pinned, GitHub refuses it, nothing merges, and the next pass pins the new head. The `done` stage records `developAutoMerge`, `developAutoMergeError` and `heldUntil` (#134)
- The factory also holds approved work in its own repository that changes a quality gate or the test guard (`quality/`, `scripts/crap.mjs`, the Stryker and Vitest configuration, `.jscpd.json`, the CI workflows, `test-weakening.ts`). It is handed over as a draft pull request for the owner to read, like a change to agent configuration, and its note asks for no evaluation, since none measures a gate (#139)
- A repository can declare fix commands (`fixes`, next to `checks` in its settings), such as `pnpm prettier --write .` or `pnpm eslint --fix .`. Before each round of checks the run executes them in the sandbox on the builder's work. When they change files, the change is committed on its own as `style: apply the repository's fixes` and pushed, and the checks, the guards and the review take that commit like any other. A fix that fails or runs past the check limit is recorded and leaves the work as it was, the fixes after it in that round do not run, and the checks still decide. Fixes never run twice on the same commit. The settings form saves them with the limits of checks (eight commands, one line of at most 500 characters each), and the evaluation suite takes the same step. A repository with no fixes runs as before (#167)
- A handed-over pull request that a person merges is now carried to the release. Every two minutes the `integrate-after-ci` cron looks at handed-over tasks, and when a person merged the task's pull request it marks the task integrated at that merge, advances `develop` and makes the pre-release, as after the factory's own merge. A release then ships it and closes its issue with the version, started by the release train in `auto` or by a person; nothing is released at the merge itself. Before, the task stayed handed over, so its issue was never closed by a release (#139)
- The owner can withdraw a send-back whose run has not started. While the task waits in `intake`, the task page offers "Withdraw send-back" (`POST /api/panel/tasks/<id>/withdraw`): the queued run is removed, the task goes back to the stage it was in with what the send-back cleared (a resolved commit, a wait for checks), and the decision is recorded as `withdrawn`. The owner can then send it back again with the right note, a failed task included. A run a worker already took cannot be withdrawn, and a run that starts after its send-back was withdrawn stops before doing anything. A send-back that reaches the task lock after the integration finished is now refused, so a run never starts on work that is already merged (#115)
- The coordinator moves the fix of a failing test ahead of the work it blocks. When one test fails on two or more tasks of a repository within six hours and a queued task's issue names that test (in a code span, in quotes or in plain text), the coordinator decides `prioritise`: in `auto` the fix's `run-task` job goes ahead of the repository's other queued jobs, and those jobs are held, including any queued later, until the fix integrates or fails, or waits for a person (a question or a handoff), when each gets back the time it had. While the fix is on its way, a task whose current failure names the test is not sent back to fail the same way. One fix is held at a time per repository, a retried fix is decided again for its new job, and in `trial` the decision is recorded and no job moves (#143)

- A scheduler decides which queued task runs next and holds back an issue that is not ready to build. Every two minutes the `schedule` cron reads the queued `run-task` jobs of tasks in `intake`. For a task's first run whose issue it has not judged in its current form, a judge built with `buildAssistant` answers `ready` or `needs_refinement` (no observable acceptance criterion, more than one independent change, or a decision only the owner can make), with what is missing and one question; an answer that does not parse counts as `ready` and its error is recorded. In `auto` a task that needs refinement does not start: its queued run is removed, the question is posted on the issue and the task waits in Waiting for you, and the owner's answer puts it back in the queue with the answer in the builder's prompt. The runs that are due and not held are then ordered: lower `priority:N` first (an issue with no such label right after `priority:5`), then `bug`, then the issue more queued issues name in their `Blocked by` line, then the oldest. In `auto` the order is applied by exchanging the `available_at` times the queue already had, so no run starts earlier than the earliest of them, and a job a worker holds, the coordinator holds or that is not due is never moved. Each decision is a `scheduler_decision` row. A queued card on the board shows its place in the queue, its priority, bug and how many issues it unblocks, and the readiness verdict. `FACTORY_SCHEDULER_MODE` is `off`, `trial` (decide and record, change nothing; the default) or `auto` (#201)
- The coordinator acts on more of what it used to hand to a person. A failed task whose checks still fail is sent back on its branch with what those checks printed; one that ran out of time is sent back to continue from its branch; one where the agent changed nothing is sent back once and escalated the second time. A fact the coordinator could not read is escalated only after an hour of retries, and an integration branch that stays red gets one `factory` issue for its fix instead of a person (#231)
- Every running card on the board says what works on the task right now: the agent, its model when the stage recorded one, and its step (planning, building, fixing findings, reviewing), with the attempt or the review round past the first, or the checks the factory runs when no agent works. A card that is not running says, more quietly, which agent and model worked on it last. The line moves with the task through the panel's event stream, with no reload. `claude-code` shows as Claude Code, `codex` as Codex, and any other agent by its own name (#212)
- A repository has a second list of checks, the integration checks, which a later step will run on the merge of the work with the integration branch, after the repository's checks. The settings form has a box for them under the checks, with its own assistant, and saves them with the limits of checks. They are proven like the checks (`POST /api/panel/repositories/<owner>/<name>/checks/prove` with `kind: 'integration'`, and `GET` with `?kind=integration`): the sandbox runs the repository's checks first so the project is installed, then the proposed integration checks on the head of the integration branch, and only the integration checks that passed are saved, with the commit. The repository's checks run in that proof are shown with their output and never saved. A check typed by hand is named as not proven until a proof runs it. Proofs and jobs stored before this change are read as proofs of the checks (#227)

- The coordinator acts on failed checks that a handoff kept no output of. When neither the handoff nor the factory's own checks quoted them, it reads the checks that failed on GitHub for the head of the pull request, with the error lines of each GitHub Actions job's log (or the annotations of any other check), and sends the task back on its branch with them. A read GitHub refuses is retried on the next passes, like any fact it could not read. When that pull request conflicts with its base, the coordinator decides the new `merge_base` action: the factory merges the integration branch into the work branch itself, with no agent, and the checks and the review read the merge. If that merge conflicts, the failure names the files, and the coordinator sends the task back to the agent to resolve them (#251)

### Changed

- When the builder answers a review by changing nothing, the reviewer reads its reasons on the same commit once before the task goes to a person. An approval then goes on to merge; a review that still blocks hands the task over as before (#385)
- Approved work that is not integrated yet moved from the Delivered column to Merge, next to the merge job and the pull request it opens, so Delivered holds only integrated work waiting for a release. The Merge column's header counts its cards as merging, opening the pull request, waiting for CI and awaiting merge, and a card that is approved but neither merged nor waiting for CI reads "approved, awaiting merge" (#377)
- The banner of a stopped line says what the line holds back. With `FACTORY_LINE_STOP_SCOPE=fix_first` it says the fix goes first and everything else keeps running; with `hold` it still says nothing else runs or integrates there. `GET /api/panel/tasks` returns each stopped line's `scope` (#377)
- A review now pushes toward fixing its findings in fewer rounds. The reviewer names the class of each defect, the invariant a fix must hold and every instance of it in the change, in one finding and in the same round. From the second round on, a new blocking finding goes only on code the task changed since the last review or on another instance of a class already named, or on unchanged code the change breaks, with the evidence of what breaks; a concern about code that was already there and that the change does not break is minor. A finding the builder declined with a reason stays blocking only when the reviewer says why the reason is wrong, and the reviewer now gets the builder's answer to the review even when the task has no plan, and still after a rework for failing checks. The builder, in turn, fixes the class rather than the quoted line, writes a test per instance, reads its whole change again for the same class before it finishes, and declines a finding only with a concrete reason and its evidence. (#375)
- The deploy's evaluation check refuses a run only when the mean cost per case more than doubles the baseline's, where it refused a rise above a quarter. A lower pass rate still refuses it as before (#378)
- A run in a repository with a large knowledge base no longer spends minutes copying it into the sandbox. The knowledge slice was copied into the sandbox one file at a time, about half a second per file on E2B, so a slice of nearly a thousand files took about eight and a half minutes before the first agent started. On E2B it is now written 200 files per request, and 977 files took 4.4 seconds in a test sandbox. The log line `sandbox_prepared` gives the milliseconds of each preparation step (`inputs`, `branches`, `credentials`, `sandbox`, `clone`, `harness`, `knowledge`, `repository_facts`) and the total, and `failedAt` names the step a failed preparation stopped in (#373)
- The coordinator's limit of two applied actions per task now counts two families apart: reworking the checks (failed or still red checks, a run out of time, an agent that changed nothing, a conflict with the base) and unblocking the review (a scope, a review run again, a retry from a supervisor finding). A task sent back once for its checks and scoped once is still scoped on its next stalled review (#336)
- A follow-up a scope files is labelled `follow-up`, and `factory` only when the issue it comes from is not a follow-up itself. A task files at most one: a second scope names the first, and an open follow-up of the same issue, or an open issue with the same title, is named instead of filing another. A scope that puts in scope a change under `.github/`, publishing a package or editing an issue or pull request on GitHub is refused, since the factory cannot do those (#334)
- A fix the coordinator moved ahead of a repository's queue (`prioritise`) now holds the repository's other runs only until it is done, verified and reviewed, instead of until GitHub merged it, so its CI and promotion no longer stop the whole repository (#332)
- A task of the factory's own repository that changes the planning prompts (`factory/change-plan.ts`, `factory/plan.ts`) is now held for an evaluation like any other agent configuration, instead of being merged (#276)
- Merging approved work is now a stage of its own. When the review approves, the run ends by moving the task to `merge` and queueing a `merge-task` job for the approved commit, in one transaction, and that job opens the pull request and integrates it as the run did before: the same direct merge, auto-merge with required checks, promotion hold, pre-release and release mode. The board has a Merge column between Will retry itself and Delivered, where a task waits in `merge` and while its pull request is opened. A person's approve, send-back, retry, resolve and release are refused while the task is merging, and the supervisor reports a task in `merge` whose job is gone or failed, as it does a queued task with no job (#227)
- The board's cards show who works on a task in a panel of its own: the agent's name and model, on a stripe in the agent's color (Claude Code, Codex), lit and pulsing while it runs, with what it does; once it is done, who worked on it last. The checks get a panel of their own. A card now starts at a common height and grows with what it says, the title takes up to three lines and the status lines wrap, so nothing on a card is cut.
- The scheduler's two steps have their own modes. `FACTORY_SCHEDULER_MODE` now sets only the order of the queue, and the new `FACTORY_READINESS_MODE` sets the readiness judge (`trial` by default). The order can run in `auto` while the judge only records its verdicts. (#201)
- The planner is a role of its own for the change plan of every task, as it was for the plans of the Plans page. A `planner:<agent>` label on an issue, the Agents page, or `FACTORY_PLANNER` choose it, with its own model and effort; with no choice it is Codex when Codex can start, and the builder's agent otherwise. A planner apart from the builder reads the code without changing it and writes the plan, and the builder gets that plan, named by who wrote it, in a session of its own; a planner that is the builder plans and builds in one session, as before. The plan, build and review stages record the agent's model and effort next to its name, and the evaluation suite runs the same planner and counts it in the agent setup it compares with the baseline (#210)
- A builder sent back by a review works through the findings one by one. It writes a test that fails without each fix to behaviour, reads its own change since the commit the reviewer read (the only code where a later round may raise a new blocker) before it finishes, says what is missing for a finding it cannot fix inside the issue instead of half-fixing it, and lists in its summary each finding with what it changed and the reason for every file outside its plan. The same prompt runs in the evaluation suite (#207)
- The evaluation suite tells a change from chance and a broken environment from a worse agent. A case the sandbox, the network or a provider's limit failed runs once more, and when it fails again it is left out of the comparison and named; a run where that happened to more than one case in five is refused as one that measured too little. Cases that got worse are weighed against cases that got better with an exact sign test, and a run is refused when its regressions would come by chance less than once in twenty, even under the 20-point drop (#164)
- From the second review round on, the reviewer is given the blocking findings of the round before and the commit it read. It checks each of them first, reads what changed since with `git diff <earlier sha> HEAD`, and raises a new blocker or major finding only on code that changed since or on a bug that would break code already in use. Before, every round reviewed the whole change as if it were the first, and a later round often asked for something new. A run that continues after a question or a send-back reads the earlier round from the `review` table, and evaluation cases do the same (#155)

### Fixed

- A task a person resolved from the panel no longer leaves its issue open for good when its resolving commit reaches the release branch through the `catch-up` cron rather than a tagged release. The issue is told which branch holds the commit and closed; an issue the agent already closed gets no comment (#389)
- The board and every reader of its task list answer in about half a second instead of eight: the factory's database runs without JIT, which Postgres spent compiling the card query on every poll, and `stage_event` has an index on the task and the order of its events (#386)
- A task whose sandbox stream dropped while e2b could not tell what became of the sandbox (`its state is unknown`) runs again on its own, like any other lost sandbox, instead of staying failed (#384)
- The banner of a stopped line printed how long the line had been stopped with a fraction of a minute ("5h 9.406216666666694m"). Durations on the board count whole minutes now ("5h 9m") (#377)
- A later review round no longer blames the task for what a merge of the integration branch brought in. The reviewer read `git diff <reviewed commit> HEAD`, which holds every commit that merge brought, and raised findings such as "the branch adds unrelated job-backend functionality" against work the task never wrote. It now reads the task's own commits since the reviewed one, leaving out merge commits and anything the integration branch already holds. (#375)
- A builder reworking a review was told to read `git diff <reviewed commit> HEAD`, which is empty while it works, since the factory commits after it. It now reads its edits against the reviewed commit. (#375)
- The builder starts with the project installed: the factory runs the repository's `install` check in the checkout before the builder's first pass in a sandbox, so it can run the tests it is told to run. What the install changes in the checkout, such as a rewritten lockfile, is put back, so it never reaches the builder's commit; the dependencies git ignores stay. A run resumed from a snapshot is not installed again, so the builder's uncommitted work is kept. An install that fails does not fail the run, and the builder is told, with the install's last lines. The `build` stage event records the install (`install: { ok, seconds, tail }`), and its time is the `install` step of the `sandbox_prepared` log line (#240)
- A changesets publication whose Version Packages pull request failed a check on its head no longer blocks the next release. That release is the only way the fix reaches the release branch, so the factory now promotes it, from the panel or the release train, and records the stalled publication as `failed`, superseded by the promotion. The tasks of the superseded publication are released and their issues closed by the next publication. While the Version Packages checks pass, run or have not reported, releases are still refused (#367)
- An evaluation case prepares and lets through a planner apart from the builder and the reviewer, as a task's run does, so a reviewer other than the planner can be evaluated (#358)
- The back-merge after a changesets release is merged as soon as it does not conflict when the integration branch requires no status check. It used to wait for every check on the released head, so a failed Dependabot run there, or a branch that runs no CI, held it open and left consumed changesets on `develop` (#365)
- The Version Packages pull request and the back-merge wait only for the checks their target branch requires, so a red check that branch does not require (`Dependabot`, a matrix job) no longer holds a publication, and every release refused behind it, forever (#343).
- A required check that fails on a pull request while the integration branch has no run of it yet keeps the task waiting, for up to six hours, instead of sending the work back for a failure the base may have; a repository whose CI runs only on pull requests has no run on its integration branch until a promotion opens (#344).
- A blocker in the same repository whose task found the issue already resolved on the integration branch no longer blocks, and the reason of a blocked task names the blockers still open each time they are read again (#345).
- A back-merge that conflicts with the integration branch shows on the health page, with its link, until the conflict is gone, and is logged once; before, it waited for checks GitHub never runs on a conflicting pull request (#307).
- An agent no longer asks again for the release of a head whose release pull request already conflicted with the release branch, so the same refusal is not opened and recorded once per integration; a person may still ask (#346).
- A deploy no longer stops the crons for as long as a run lasts. The main process (`aifactory.service`) now starts with `FACTORY_SERVER_ONLY=1`: it serves the panel and the webhook and runs the crons, takes no job, and stops within 2 minutes. The workers run every job (#363)
- A deploy no longer waits for the runs in progress to end: the workers are restarted without blocking and each comes back on the new build once its run finishes, so one long run no longer holds the next deploys for hours (#356)
- A task handed over a second time on the same head now gets a coordinator decision, or at least an escalation, instead of none: a handoff is identified by its head and its event, as a failure is. Decisions recorded before are moved to the handoff they were decided for (#335)
- The builder is no longer told that the required checks failed when the coordinator sends it a scope decision about the review (#338)
- Reworks for failing checks and review rounds have separate budgets, so a run whose first commits failed the checks still gets every review round instead of going to a person after its first review (#347).
- The review and the facts about the diff measure the change from the integration branch as it is when the review starts, so files another task brought in through a merge of that branch are no longer listed as changed outside the plan (#348).
- A merge of the integration branch into approved work keeps the approval when the task's patch is the same before and after it, so the merge goes on to integration with no new review (#349).
- Send-backs for a conflict and merges of the base (up to six), and checks of a `Blocked by` issue, no longer use up the three automatic runs of a task, so approved work that only needed the base merged stops reaching a person (#350).
- A handoff made after the last rework broke the checks records the cause `checks_broke_after_review`, so the coordinator no longer treats it as a review plateau (#351).
- E2B's `403: team is blocked: credit_exhausted` is now an environment failure that retries by itself, and the doctor shows it as the sandbox provider refusing. It used to go to a person as a failure of the work, which the coordinator escalated with no action (#339)
- A run no longer fails for want of a free sandbox slot after waiting 20 minutes. Before its first stage it waits in the queue while the account already has as many sandboxes up as it allows (10 on E2B unless `E2B_MAX_SANDBOXES` says more), for up to three hours (#341)
- The evidence of a failed CI job keeps the line that reports the failure (a test marked `FAIL`, the runner's `##[error]`) when more than forty lines match, reads a line a script starts with `✗`, and no longer takes a package manager's `WARN` for it, so an agent sent back after failing checks reads why they failed instead of the errors passing tests logged (#326).
- A release is refused while a changesets publication of the repository still waits for its Version Packages to publish, so a promotion no longer lands changesets on the release branch that keep the workflow versioning instead of publishing (#319).
- A run refused for the sandbox provider's concurrent limit waits for a free slot, as an evaluation case does, instead of failing and waiting about 20 minutes for its retry (#314).
- The release train releases a repository that keeps working: a queued task no longer holds it, and a running one holds it only until the oldest integrated work has waited an hour (#303)
- Checks that fail for the first time on the same promotion head become one issue that names them all, so one task fixes them together instead of one task per check waiting on the others forever (#306)
- A red integration branch starts its fix after 30 minutes instead of 2 hours, and its clock no longer restarts when another of its checks goes red or its checks run again (#282)
- The issue the factory files for a check that fails on a promotion is labelled `priority:1`, so its fix runs ahead of the queue instead of after every other task while the red base holds the repository's deliveries (#300)
- `pnpm evals:check` no longer fails every case as an environment failure while the factory's runs hold every E2B sandbox: a case waits for a slot, asking again every 30 seconds for up to 20 minutes (#261)
- `change_failure` no longer counts a delivery whose next run only merged the integration branch after a required check failed there too; that failure was the base's, not the work's (#274)
- A task that failed because its harness would not install in the sandbox (`claude did not install`, `codex did not install`) or because the provider ended the sandbox in the middle of a command (`The sandbox was killed or reached its end of life`) now runs again on its own like any other failure of the environment, instead of waiting in Failed for a person (#266)

- Approved work merges within minutes instead of waiting for a worker to finish a run. The `merge-task` and `resume-task` jobs, which take seconds, are queued ahead of every queued run, which can take an hour each (#259)
- A task sent back on its pushed branch that asked a question, got an answer and then changed nothing no longer fails with `the checkout is not the pushed commit`. The resumed run used to take it as a new issue the agent found already done and checked the base commit; it now checks and reviews the head of its branch (#255)
- The board leaves cancelled tasks out. Their issue was closed or lost the `factory` label, so they no longer count in Needs a person (#253)
- E2B refusing a sandbox because the account already runs its concurrent limit is now an environment failure. A task that meets it is retried on its own instead of going to a person, and the evaluation suite runs such a case again instead of counting it against the configuration (#249)
- A run the coordinator sends back after it ran out of time or changed nothing now goes on with the branch head to the checks and the review when the agent changes nothing and no review approved that head. Before, a send-back with the factory's own note skipped that path and failed at `push` with "the agent made no change to the repository" (#247)
- A task that failed when GitHub refused a call for the spent rate limit, before the factory named that refusal (#236), now runs again on its own like any failure of the environment. Its reason still reads "API rate limit exceeded", which the factory did not recognise, so it waited for a person (#239)
- Closing an issue, or removing its `factory` label, now cancels its task. A task that is queued, working, waiting for an answer or failed moves to `cancelled` with a stage event that says why ("the issue was closed" or "the factory label was removed") and who did it, and its queued `run-task`, `merge-task` and `resume-task` jobs are deleted in the same transaction. A job a worker ever took is left alone. A run whose task is cancelled stops at its next stage: it records nothing more, does not fail the task, queues no `merge-task` and stops its sandbox, and a job taken just before the cancel stops before it starts one. Before, the task stayed queued and later ran an agent on work nobody wanted, and a failed one could run again on its own. A finished, handed-over or released task is not touched, and reopening the issue brings nothing back (#237)
- A deploy no longer leaves the factory with no worker for as long as the slowest run takes to finish. The worker unit was ordered after the main service, so restarting every process started the workers only after the main process drained its run and came back. Each worker now restarts on its own, and only the deploy and the main process run the migrations (#228)
- The factory no longer spends the GitHub App installation's hourly request budget and then fails every call until the reset. A call GitHub refuses for a rate limit (403 or 429 with no request left, a `retry-after`, or a body that says the limit was exceeded) is now raised as `RateLimited` with the reset time, so logs such as `blocked_check_failed` say "GitHub rate limit spent ... until <time>" instead of a plain 403, and a run that fails this way is retried on its own like an environment failure. Once less than a tenth of the installation's core budget is left, the polling crons (`integrate-after-ci`, `knowledge-sync`, `poll-answers`, `publish-changesets`, `watch-main`, `watch-promotions`) skip their passes until the reset and log `github_pass_waits` once per reset. `integrate-after-ci` reads the head of an integration branch, its checks and its required checks once per repository per pass instead of once per waiting task; with 15 tasks waiting on a red base that was about 120 requests every two minutes. Every cron pass that calls GitHub logs `github_requests` with the requests it made by kind of token and what GitHub reported left of the budget (#232)
- A task blocked by an open issue no longer goes back into the queue every half hour while its blocker is still open. The `retry-due` pass reads its blockers first: while one is open the task stays failed, the check is recorded on its failure (`blockedCheckedAt`) and the next one is half an hour later. It runs again only once none is open, so the queue on the board holds only work that can start, and a blocked task no longer takes a start of the pass from a task that can run. A blocker that cannot be read is logged and read again on the next pass (#224)
- A check that fails on the head of the integration branch too no longer fails every task of the repository after its reworks. When the builder answers failing checks with no change, or the same checks fail again after a rework, the factory runs those checks on the commit the work started from, at most once per check in a run; if they fail there too, the run stops, the task fails with a reason that names the checks and that commit, and it runs again on its own after half an hour, an hour and two hours ("waiting for the base to pass" on the board), then goes to a person through the coordinator. An evaluation case in the same state is left unmeasured. (#219)
- A run whose last rework breaks a check no longer fails when an earlier commit of the same run passed the checks and was reviewed. That commit's tree comes back as a new commit (history is not rewritten), the checks run on it, and the work goes to a person as a draft pull request with that review and what the last rework broke. When the checks fail there too, the run fails as before. (#216)
- A rework round in which the builder changes nothing no longer fails the task. After a review, the builder's answer goes to a person as a draft pull request, with the reason it gave, and the same commit is not reviewed again. After failing checks, the checks run again on the same commit, within the attempts the run already has. (#214)
- An evaluation run that reaches the suite's 4 hour timeout now leaves its results. Each case is written to `.evals/` as it finishes, the cases the run selected are written before the first one starts, and no case starts once the time left is shorter than the longest sandbox limit of the run's repositories plus ten minutes (`EVALS_START_MARGIN_MIN` sets it). Cases still running five minutes before the timeout are abandoned: their sandbox is stopped, an agent that answers after that starts nothing more, and they are named as left. A baseline run that left cases writes no `baseline.json`, and the deploy check fails when a quick case was left unmeasured. The time counts from the start of the test, so choosing the cases and reading the agent setup count against it, and a setup read that hangs fails the check with its reason instead of the test timing out with nothing written (#180)
- A run that fails because the sandbox provider lost the sandbox (`The sandbox could not be reached and its health probe failed`) is now read as a failure of the environment: the task runs again on its own, and the evaluation suite leaves the case unmeasured instead of counting it against the agents (#176)
- A task whose runs keep failing with `fetch failed` before any agent runs no longer retries every five minutes forever: once the failures have gone on for more than an hour, the runs count against its allowance and the task goes to Needs a person (#178)
- A required check that fails on the integration branch too no longer sends every task back to its agent. When a required check fails on a task's pull request, the factory now reads the same check on the head of the integration branch. If it fails there as well, the task keeps waiting, auto-merge stays pinned to the verified commit, and the `integrate_after_ci` log line lists it under `waitingOnBase`. Once the integration branch passes every check it was blamed for, the factory runs the task again only to merge that branch into the task's branch itself, with no agent, so the checks run again on a commit with the fix, and the merge is verified and reviewed like any other work. A merge that conflicts goes to a person, naming the files. A check that fails only on the pull request is sent back as before, and nothing merges while a required check is red (#153)
- A task sent back on a branch whose pull request is closed is no longer judged on that pull request's old head. GitHub does not move the head of a closed pull request, so when the agent changed nothing the run read the stale state and handed the task over again, and the coordinator sent it back the same way. The run now goes on from the branch's head to the checks and the review, then reopens the pull request (or opens a new one when GitHub will not reopen it, logging why). When the branch has nothing ahead of the integration branch, the task is handed over with that said, since GitHub refuses an empty pull request. The coordinator treats a closed pull request's merge state as unread and escalates it as `unknown` instead of sending the task back (#144)
- An E2B sandbox whose process died no longer holds one of the account's sandbox slots until its session ends. Every sandbox the factory creates carries metadata with an `aifactory` mark, its owner (a task and its run, an evaluation, a proof of checks or a plan) and the lease of the process that made it, and each process that creates sandboxes renews its lease in `sandbox_lease` every 30 seconds. Every five minutes the `supervise` cron stops the factory's sandboxes whose task left the stages that hold one or moved to another run, and those whose process exited, which it sees on its own host on the first pass after the exit. A process on another host is suspected when its lease goes two minutes without a beat, and its sandboxes are stopped only if it is still quiet two minutes after that, so live processes keep their sandboxes after a database outage. A sandbox with no metadata is stopped after ten minutes. A sandbox whose metadata lacks the factory's mark belongs to another application and is never stopped. Each stop is logged with the sandbox id and the reason, and the doctor shows how many sandboxes are up against the account's limit (`E2B_MAX_SANDBOXES`, 10 by default) and how many have an owner at work (#170)
- A task stopped by a network outage before any agent ran no longer uses up its automatic retries. When the host loses its network, a run fails with `fetch failed` while it reads the issue or creates the sandbox; that run is no longer counted against the three automatic runs, so the task runs again on its own and finishes once the network is back, where before an outage of a few minutes could leave it failed and waiting for a person. Reading an issue now also asks GitHub again, with a pause, when the network drops the request or GitHub answers with a 5xx (#136)
- The task board loads in under half a second instead of about 20, and no longer keeps the database busy while the panel is open: `stage_event` gets an index on its task, its stage and its order (#166)
- The factory no longer integrates a change to its own agents by itself. When approved work in the factory's repository touches agent configuration (the harnesses, `review.ts`, `evidence.ts`, `guards.ts`, the models, the prompts under `src/server/agents/`), the task is handed over as a draft pull request with the cause `agent_configuration`, the paths it changed and what to run, and nothing is merged. Before, the factory merged such a change into `workspace` as soon as the checks passed and the reviewer approved, with no evaluation. A fork names its own repository with `ownRepository` (#139)
- An issue is no longer closed when its work is integrated, before a release ships it. The factory's pull request began with `Closes #<issue>`, so in a repository whose default branch is the integration branch GitHub closed the issue on that merge. The body now names the issue with no closing keyword, and the issue is closed on release, with the version, as for every other repository (#138)
- A promotion into `develop` that waited with nothing pinned is now pinned. A repository whose work was integrated before promotions were pinned, or whose pin GitHub refused, kept its promotion pull request open with no auto-merge, and its work never reached `develop`. Every two minutes the `integrate-after-ci` cron now finds such a repository (integrated work that no release holds, no promotion waiting, and an open promotion from the factory) and turns on auto-merge pinned to the promotion's head, or merges it at once when GitHub finds it clean. A repository it cannot look at is logged and looked at again on the next pass (#134)
- The coordinator no longer asks for a release while `develop` holds nothing the release branch lacks. Before, integrated work whose promotion had not merged was taken as ready, and `release()` was refused because GitHub found no commits between the release branch and `develop`. The train now reads how far `develop` is ahead of the release branch with its head, and waits while that is zero (#128)
- Approved work whose pull request conflicts with the integration branch is no longer thrown away. Before, the factory deleted the task's branch, which closed the pull request, and ran the task again from the start. Now the task goes back on its own branch with a note to merge the integration branch, regenerate generated files with their scripts, and change nothing else; auto-merge is turned off first, and the merge then goes through the checks and the review. A task whose branch is gone still starts over. A commit the agent makes by itself, as `git merge` does, is now pushed as it is, where before a clean checkout read as no change (#122)
- The coordinator no longer sends a task back with the output of its failed checks when its pull request conflicts with the integration branch. For a handoff on failed checks the agent did not answer, it now reads the pull request, and when GitHub reports a conflict the note tells the run to merge the integration branch and regenerate generated files, the same note the panel gives approved work that conflicts. A pull request it cannot read is escalated as `unknown` and nothing is sent back (#132)

## [0.3.0] - 2026-11-15

### Added

- A repository can have its own limit for a run, in minutes, saved on the repositories page, with the default staying at 90 (#103)
- Checks proposed for a repository can be proven before they are saved. `POST /api/panel/repositories/<owner>/<name>/checks/prove` queues the `prove-checks` job, which runs the proposed checks in order in one isolated sandbox on the head of the integration branch and stores only the ones that passed, with the commit they passed on. A check that fails on the base is not saved and comes back with its output; one still running at its time limit is reported as too slow for a run, with its duration, and not as failed. `GET` on the same route reads the last proof. The settings form still saves what the owner types, and its answer and the repository list now name the saved checks that no proof ran (`unprovenChecks`). The panel does not show any of this yet (#71)
- A repository doctor examines a repository before a task fails on it. `GET /api/panel/repositories/<owner>/<name>/doctor` answers with one item for each diagnosis: Issues turned off, what the GitHub App reaches and may do, the events it subscribes to, the `workspace` and `develop` branches, the `factory` label, auto-merge when the integration branch requires checks, a required check that reported on no recent commit or pull request, a required check the factory has no check for, how the repository publishes (changesets, a workflow that runs on a tag, or nothing), the recipe, and the sandbox provider refusing. Each item carries a status (`ok`, `warn`, `blocked` or `unknown`), the cause, the repair, a link and whether the factory can make the repair. What could not be read is `unknown` with what was tried, never `ok`. `POST .../doctor/repair` creates the missing branches or the label and refuses any other item with the reason. Enabling a repository runs the doctor and answers with the report, and a blocked item does not stop it. The last report is kept in `repository.doctor` and the publish mode in `repository.publish_mode` (#70)
- The webhook recognises more than a labelled issue. A new comment on an issue or a pull request, a submitted review, a completed check suite or check run, and an issue that is closed, reopened or loses the `factory` label are stored in `ingress` with the outcome `routed` and a code that names what happened. Nothing acts on them yet: a routed delivery creates no task and queues no job. Tasks have a `cancelled` stage that no run enters yet, shown under "Needs a person". The Setup page has a "Webhook events" line that reads what the GitHub App subscribes to and names the events it does not receive, with a link to the App settings (#59)
- Before it changes anything in a new task, the builder writes a plan: the files it will change and why, the order, the risks, the tests that prove it and what it leaves out. The plan is stored, shown in the pull request and on the task page, and given to the reviewer, together with the changed files the plan does not name; the build continues the session that wrote it, and a task sent back keeps its plan instead of planning again (#33)
- The review no longer approves a change that weakens a test that was there before it: a test case removed, fewer assertions, or a skip, `only` or todo added. It is a blocker in an issue labelled `bug` and major otherwise; when the issue names the file or the test, the reviewer decides (#34)
- The `watch-promotions` cron watches the open promotion pull requests of every enabled repository (`workspace` into `develop`, `develop` into the release branch, and the Version Packages pull request). A GitHub Actions job that failed is rerun once; when it fails again, or when a check such as CodeQL fails, the factory opens an issue with the `factory` label carrying the check, the run and the error lines of its log, so an agent fixes it without anyone reading the log first. The same failure on a later commit is a comment on its issue. A secret scanner's failure gets an issue without the label, for a person. `FACTORY_PROMOTION_ISSUES_PER_PASS` caps the new issues per repository and pass (three by default) (#31)
- The factory measures itself every hour: first-pass checks, rework rounds, first-review approval, time to first review and to delivery, cost per delivered run, change failure and hours to release, per repository and for all of them, as daily points. Each series is read against a control band (mean and standard deviation of the 30 days before its last 8 points, with the Western Electric rules, in the direction that is worse). A drift is only recorded, a run out of band shows on the Health page, and a point beyond 3 sigma opens an issue, once per metric and repository within the window. Detection uses no model (#32)
- Sandboxes can run on E2B with `FACTORY_SANDBOX=e2b` and `E2B_API_KEY`, under the same domain allowlist, with credentials attached outside the sandbox and renewed while a run works; a run plans its agent passes for the hour E2B's free plan allows, or for `E2B_MAX_SESSION_MS` (#26)

- An evaluation suite of 30 tasks the factory delivered, in six repositories, run by the real agents along the factory's path (sandbox, checks, diff guards, review, rework) without pushing anything. `pnpm evals` runs the quick five and compares them with `evals/baseline.json`; `pnpm evals:cases` rebuilds the cases from the database. A deploy that changes a prompt, a harness, a model or the sandbox image now runs the quick cases first and stops, before the build, when the pass rate drops by more than 20 points or the mean cost per case rises by more than 25% (#35)

Any other refusal fails as before (#51)
- A task that finished with no change now moves from Already resolved to Released once the commit it was resolved at is on the release branch (the one the owner set, or the default branch). Every release that completes, the factory's own or a changesets publication, checks the resolved tasks of its repository against the promoted commit. The `catch-up` cron checks the ones already there, 25 per pass, and a task moved once is never checked again. The `released` stage names the release branch and the resolving commit; no tag is recorded and its issue, closed when it was resolved, gets no comment. A task whose commit is not on the release branch yet stays in Already resolved (#50)
- A changesets publication no longer fails when the release workflow pushed `changeset-release/<release branch>` but did not open the Version Packages pull request, as happens where the organisation does not let Actions open pull requests. When that branch is ahead of the release branch, was committed after the promotion and has no pull request, the factory opens Version Packages from it, naming the promoted commit, and the publication keeps waiting until it merges that pull request as usual. A branch committed before the promotion is ignored, and with no such branch the publication ends as before (#49)
- A task that finished with no change, because the code already did what its issue asks or a person resolved it another way, no longer sits in the Delivered column forever. Delivered now holds only work that waits for a release, and such a task moves to a new Already resolved column, since no release will ever carry it. A task whose work was merged into the integration branch stays in Delivered until a release carries it. The tasks already in that state move on the next load of the panel (#47)
- A release in a changesets repository no longer counts as waiting the changesets that an earlier release already consumed on the release branch while `develop` still holds them. A changeset waits only when the comparison of `develop` with the release branch lists it as added since their merge base; with none added, the release is the factory's own or is refused naming the published package, as for a repository with no changeset. A publication whose release run on the promoted commit finished without opening a Version Packages pull request no longer waits forever: after a 10 minute grace window, when every check on that commit completed, the factory releases the promotion as its own patch version, releases its tasks and closes their issues. When a check failed, or the promotion changed a package changesets publishes, the publication fails and the task page shows why (#48)
- A release in a changesets repository with no changeset waiting is no longer refused when every change since the release branch is in packages changesets never publishes. The factory reads which files `develop` changes, maps each one to the packages it is under, and when none of them is published (private, listed in `ignore` of `.changeset/config.json`, or no package at all) it promotes `develop` and makes its own release: the tag, the released tasks and their closed issues. When a published package changed, the refusal stays and now names the package. The factory's own version now follows the highest `vX.Y.Z` tag of the repository, since in such a repository the latest release is a package's tag (#46)
- A release the factory tags itself now releases every task whose work the promotion carries, not only the one it was asked for. Each finished task whose merge is in the promoted commit moves to released with the tag, and its issue gets a comment naming the version and its release, then is closed; the task that asked for the release is treated the same way. Before, the other tasks stayed done and no issue was closed. An issue GitHub will not close no longer stops the release or a changesets publication: the reason is recorded on that task and in the result (#45)
- When a promotion check fails again on a new commit after the fix for its open issue was integrated, the `watch-promotions` cron now opens a new issue for the factory, linked to the previous one, instead of commenting on an issue nobody works on until the release. While the fix is not integrated yet, the same failure is still a comment on its issue, and the cap on new issues per pass still applies (#44)
- A required check that ran twice on the head commit, as a workflow on both `push` and `pull_request` does, no longer reads as passed when one of its runs failed. GitHub blocks the merge on that failed run, so a release waiting for its checks waited forever instead of being refused. The factory now counts a required check as failed when any run of it on the commit failed: the release is refused with the check's name, and an integration is sent back with the failed run's report. A check whose runs all passed is not failed, and one with no report is still silent (#43)
- An E2B run no longer fails with `2: [unknown] terminated` when the connection to a sandbox that is still alive drops in the middle of a command. The factory reattaches to the command by its pid, up to six times with a pause that grows from 1 to 15 seconds, all within the command's own timeout, and returns its real exit code and its whole output, kept in files inside the sandbox, so the agent's JSON reaches the factory complete. Lines that came while the connection was down reach the task page when the command ends. A sandbox that stopped or does not answer still fails the run at once, and when every reattach fails the error names the command's pid and the last failure (#41)
- The review no longer reads a test case retitled in its own file as a removed one, so a change that has to update a count or a version in a test title can pass. Each new name a test file gains, and that no file in the diff lost, stands for one name the file lost. When the file keeps its assertions, the retitle is only a minor finding that asks the reviewer to check the new title. A case removed with no new one in its file, and a file left with fewer assertions, still stop the approval as before (#42)
- When a required check fails on a pull request in auto-merge, the work no longer goes back to the agent with only a link it cannot open from its sandbox. The `integrate-after-ci` cron reads each failed check on the server with the repository's token and puts its evidence in the note: the error lines of an Actions job's log, or the annotations and summary of any other check, read the same way `watch-promotions` reads them. The link stays in the note. When the required check is an aggregate job whose log only says that a job it depends on did not succeed, the note also names the other checks that failed on the same commit, marked as not required, with their links and error lines. When GitHub will not give the evidence, the note keeps the link and says the log could not be read, the reason goes to the cron's log, and the work is still sent back (#40)
- A release into a branch that requires status checks no longer fails because GitHub refuses to merge a release pull request whose checks have not reported. The factory turns on auto-merge pinned to the head it saw, and the `integrate-after-ci` cron finishes the release once GitHub merges it: the tag, or the publication of a changesets repository, recorded only when the promotion is on the release branch. A required check that fails, a new push to `develop`, a conflict or a check that never reports refuses the release without retrying it, and the task page shows why; only one release per repository waits at a time (#28)
- A promotion job whose rerun GitHub refuses (403 or 404, as when the GitHub App may not write Actions) no longer stops the `watch-promotions` pass for its repository every five minutes without filing anything. The first attempt becomes the evidence: the issue opens in the same pass with the lines of the job's log and says the job could not be rerun, and the refusal stays in the pass's errors so the missing permission shows in the log. Any other failure of the rerun still fails the pass (#39)
- A task sent back is no longer charged with what its integration branch changed after its branch was cut. The review guards now read the change from the merge base, as the reviewer and the pull request do, so a release merged in the meantime no longer shows up as files changed outside the plan, as a weakened or deleted test, as a changed `test` script or as a change to `.github/`. A first run reports the same findings as before (#38)
- After a changesets release, the `publish-changesets` cron also merges the back-merge pull request the repository opens from its release branch into its integration branch, with a merge commit pinned to its head, once its checks are green; while they fail or run it stays open and is tried again a minute later. Until now nothing merged it, so every factory pull request into the integration branch failed its checks and approved tasks were sent back. No other pull request is merged this way, a fork's branch of the same name included (#37)
- A release in a repository that publishes with changesets no longer tags a version of its own that names nothing on npm: it refuses when `develop` holds no changeset, promotes `develop`, and leaves the version to the repository's release workflow; the factory then merges the Version Packages pull request once its checks are green, and when the packages are published it releases every task whose work shipped and closes its issue with the versions. Work on such a repository is also checked with `changeset status`, so a package changed without a changeset is sent back (#27)
- A task whose issue says it is blocked by issues still open no longer runs and lands in Needs a person: it waits in Will retry itself, before any sandbox, and checks again every half hour until each of them is closed (#21)
- A deploy now starts every enabled worker, a stopped one included, so the factory runs as many tasks at once as it has workers; before, a worker that stopped once stayed stopped through every later deploy (#20)

## [0.2.0] - 2026-11-10

### Added

- A failed or handed-over task that a person resolved another way can be marked resolved from its page, with a note saying where; it moves to Delivered (#10)

### Changed

- A done task whose pull request GitHub refused for a conflict with its base now runs again on its own from the new base, up to three times, instead of waiting for a person to press Retry; a merge refused for any other reason still waits for a person (#16)
- A done task whose pull request was never merged, as when GitHub refuses it for a conflict with the base, can be started again from the panel (#14)

### Fixed

- A merge GitHub refuses for a moment no longer leaves a task done with its pull request open: a 5xx or a 405 that says the base branch was modified is asked again, up to four times (#14)
- A run starting while another run makes its docker sandbox no longer removes that run's new network and fails it at the sandbox stage: a network counts as an orphan only once it is as old as a stale container (#15)
- The factory's squash merges no longer gain a `Co-authored-by` trailer for its own bot: each squash commit is named after its pull request, with no body, instead of the message GitHub composes, which lists every commit author; commits are also signed with the bot user's own email, which needs the new `GITHUB_APP_BOT_USER_ID` (#13)
- A repository's test that starts a server on localhost and fetches it no longer fails in the docker sandbox: localhost is named on 127.0.0.1 alone, as on a hosted runner (#12)
- A repository's test that a subprocess is gone no longer fails in the docker sandbox: the sandbox now runs an init that reaps exited orphans (#11)
- A Claude Code run that printed its result before a background command kept it alive past the timeout no longer fails the task (#8)
- The factory can push a change to `.github/workflows`: its installation token now asks for the `workflows` permission (#9)

## [0.1.0] - 2026-11-08

### Added

- An issue labelled `factory` in an enabled repository becomes exactly one task, and a repeated webhook delivery does not create a second (#6)
- Each task runs a coding agent (Claude Code or Codex) in an isolated sandbox with an explicit domain allowlist, with credentials attached outside the sandbox (#6)
- A pull request opens only after the configured checks pass on the pushed commit, and an independent reviewer approves it (#6)
- Failed checks or a review that asks for changes send the work back to the same agent session, and a person takes over after three attempts (#6)
- An agent that needs a decision asks on the issue, and the answer resumes the same session (#6)
- The factory merges its own pull request into `workspace`, tags a pre-release on `develop`, and leaves the release to `main` to a person or, when enabled, an agent's verdict (#6)
- A red `main` after a release opens a revert pull request, which the factory never merges (#6)
- The panel shows the board, the inbox, each task's timeline, evidence, reviews and cost, live, and lets the owner approve, ask for changes and retry (#6)
- The panel lists the repositories the GitHub App reaches, enables them, and sets checks, domains, branches, agents and release mode for each (#6)
- New jobs and plans of several issues can be started from the panel, and the task still comes from the issue's webhook (#6)
- A chat assistant and a guide on each page read the factory's state and ask before changing anything (#6)
- Every agent reads the owner's knowledge base, written as an Open Knowledge Format 0.2 bundle, and notes what it learned (#6)
- The panel shows what the agents do while they work, step by step, and keeps it for 30 days, with known token formats redacted (#6)
- A project can declare its install command, checks and domains in `.factory/setup.json` on its default branch, and its domains open only after the owner approves them (#6)
- The agent is told the exact commands the factory runs on its commit, in the first pass and in every rework (#6)
- An issue the code already resolves is closed with the evidence instead of failing (#6)
- The factory runs as `systemd --user` services, catches up on missed webhooks, and keeps a restorable database backup (#6)

### Fixed

- Claude Code runs on the Docker sandbox no longer fail with `claude: not found` (#1)
- A run started again after its process died can push its branch again (#2)
- A clone that stalls is cut after three minutes and tried again, instead of failing the task after ten (#6)
- A run may last 50 minutes instead of 30, and one that runs out says so instead of failing with `No such container` (#6)
- A check that fails runs once more at the same commit, so a flaky test no longer costs the agent an attempt; both runs stay in the evidence (#6)
- The checks run on a clean tree of the pushed commit, so what the agent left in ignored files no longer decides the result (#6)
- The backup check reads the whole dump and no longer fails with EPIPE on dumps over about a megabyte (#3)
